# 第一版整合驗收

驗收日期：2026-10-13。規格來源：`.scratch/vehicle-monitor/spec.md`；驗證接點為 HTTP 與實際網頁。未新增自動測試檔。勤崴路線權限沿用任務 02 的真實查核，實際方案與頻率上限仍無官方帳戶證據，預設併發 1 不代表服務配額。

## 重現方式

1. 依 README 啟動 Server、車隊 Client 與 Vite，從監控頁開啟兩個新增乘客頁面。
2. 手動點選上、下車點並送單；另外送出單筆隨機請求，再啟動限量生成器。核對乘客身分、請求、任務與車輛關係。
3. 行駛中調速，選車、定位與跟隨；關閉監控頁後保持 Python 程序執行，再開頁核對進度。
4. 使車隊全忙，取消等待請求；規劃開始後再次取消應拒絕。更改各車容量後重啟，以不同人數驗證略過等待與順位保留。
5. 同輪斷線只阻斷 HTTP，保留程序。分別在接人與載客階段阻斷指定車輛，等待超過離線門檻，再恢復；核對暫停、送達待確認、續行及完成。
6. 已開始下一筆任務後，透過 FastAPI 文件重送上一筆完成；新任務與車位不得改變。重啟 Server 後重送舊輪次回報，應拒絕。
7. 生成器斷線時暫停，恢復後維持剩餘量且不補發；僅重啟生成器不清空 Server。

## 執行紀錄

Server 使用預設設定，車隊 Client 使用 `--block-http-file .local/block-vehicles.txt`。檔案每行列出要阻斷 HTTP 的車輛 id，清空檔案即可恢復；此診斷開關保留 Client 程序與路線快取，不重啟 Server。兩個獨立 Server 輪次分別驗證限量生成及真實道路接送，使用本機 8000／8001 連接埠。生成器恢復情境另外使用本機 HTTP 代理暫時回應 503，Server 與生成器持續執行。

| 永久失聯 | 指定車長時間失聯仍保留待確認、原任務與指派，直到恢復或重新開始。 |
| Server 重啟與隔離 | 新 Server 輪次清空請求／任務，三個存活的 Client 都回到各自初始位置；舊輪次完成回應 409，新輪資料不受影響。只重啟生成器仍保留原資料。 |

路線錯誤驗收使用 `create_app(config_path, route_transport=httpx.MockTransport(handler))` 在第三方 HTTP 邊界提供可控制回應，僅用即席命令，不新增測試檔、產品假路線端點或替代道路；正常接送使用勤崴真實服務。同點行程沒有道路行駛，以零距離／零時間完成。

## 檢查與審查

Vite production build、全部 `src/*.js` 與 Vite 設定語法、Python compileall、pip check 及 git diff --check 通過。沒有既有自動測試，未新增測試檔。code-review 的 Standards 軸發現英文 merge 訊息與兩項封裝改善，已交由同一實作者修正；Spec 軸未發現可確認的功能缺陷，保留以下驗收缺口。

## 待驗項目與原因

- 實際瀏覽器新增乘客、刷新保留身分、選點標記、隨機／取消／調速操作、列表及定位／跟隨。
- 同一模型 URL 的三個模型位置與朝向互不影響、選車後路線與鏡頭目標切換。
- 實際網頁關閉／重開及同輪 HTTP 中斷時最後資料與中斷標示。
- 本機勤崴帳戶的實際方案、每日配額與頻率上限；目前沒有官方帳戶查核證據。

瀏覽器驗收工具先逾時；Windows computer-use 隨後因無法可靠辨識 Chrome URL 而停止本輪操作。以上項目沒有執行，不以語法、建置或靜態審查宣稱通過。任務 14 與依賴網頁／多模型人工驗收的任務維持 awaiting-validation；所有功能程式已實作，整份規格仍待驗收。
