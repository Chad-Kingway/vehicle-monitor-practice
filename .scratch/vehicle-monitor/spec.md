# 車輛監控系統規格

Status: confirmed

## 既定規範

- 前端使用 Vite + Vanilla JavaScript（HTML / CSS），後端使用 Python + FastAPI，通訊統一使用 HTTP。
- Server 管理車輛、需求與任務資料；車輛 Client 負責模擬及回報狀態；乘客 Client 負責提出需求；監控網頁負責顯示 Server 資料。
- 地圖與 3D 模型顯示留在前端；第三方 SDK / API 須以官方文件確認。
- `../kwmap-practice/` 僅供讀取與參考；所有修改限於本專案。

## 已確認需求

- 乘車請求包含上車點、下車點與乘車人數。
- 第一版以同一台電腦執行 Server、車輛 Client、乘客 Client 與監控網頁，完成模擬展示。
- 使用模擬車輛與乘客資料。
- Server 使用記憶體保存資料；重啟後清空車輛狀態、需求與任務，重新開始模擬。
- 區分同一輪模擬的暫時斷線與 Server 重啟：前者採下述斷線規則；後者開始新一輪，舊資料清空、車輛回到設定初始位置，乘客模擬程式重新啟動。
- 乘客送出乘車請求後，由 Server 自動派車；有空閒車輛時指派，否則等待。
- 一個接送任務由一台車執行一筆乘車請求，包含前往上車點、接人與送達下車點；每台車同時只執行一個任務。
- 乘客可見流程為「等待派車 → 規劃路線 → 前往接人 → 載客行駛 → 完成」；已確認的路線規劃失敗顯示「失敗」，失聯任務依下述規則標示「進度待確認」。第一版抵達上車點即開始送人，抵達下車點即送達，不額外等待上下客；Server 核對送達結果後確認任務完成。
- 乘客只能取消「等待派車」的請求，開始規劃路線後不能取消；保留「已取消」紀錄。
- 第一版不安排共乘，也不讓車輛同時承接多筆乘車請求。
- 車輛 Client 使用獨立 Python 程式模擬行駛並透過 HTTP 回報；關閉監控網頁不影響模擬執行。
- 地圖與車輛 3D 模型沿用舊專案；SDK / API 整合仍須依官方文件確認。
- 將舊專案車輛模型複製至本專案 `public/models/car/`，並以 `.gitignore` 排除 `public/models/`，不納入 Git 追蹤。
- 第一版按送出順序掃描等待請求，從符合條件的空閒車輛中，以到上車點的直線距離選擇最近的一台；實際行駛路線另外規劃。暫時無法服務的請求保留原順位，允許先處理後面可被服務的請求。
- 每台車有載客上限，只能承接人數未超過上限的乘車請求；超過整個車隊最大載客上限的請求直接拒絕。若合適車輛忙碌，請求繼續等待。
- 車隊預設三台車，可透過設定調整數量。
- 每台車預設最多載四人，可分別設定各車載客上限。
- 各車使用不同固定初始位置，可透過設定調整；每次重新開始模擬均回到設定位置。
- 車輛行駛共用速度倍率，預設 10 倍且可設定；乘車請求生成間隔仍以真實時間計算。
- 速度倍率須可在監控頁即時調整，從目前行駛進度繼續，不重置車位或任務；其他設定依下方設定表生效。
- 送達乘客後，車輛停在下車點；Server 確認完成並恢復車輛空閒後，從該位置承接下一筆任務，不自動返回初始位置。斷線期間已送達的車輛仍須等待恢復連線與完成核對才能接單。
- 車輛每秒回報一次位置、朝向與任務進度；監控與乘客網頁每秒透過 HTTP 更新一次。頻率可設定，採全域設定並區分車輛回報間隔與網頁更新間隔；兩者均以真實時間計算，不受行駛速度倍率影響。
- 車輛超過 10 秒未回報即標為離線並排除派車，離線門檻可設定。Server 保留原任務與指派關係，標示「進度待確認」，不立即判定失敗或將同一請求轉派其他車輛。
- 車輛無法連線 Server 時，已載客車輛沿已取得的送人路線完成送達，到站後原地等待；尚未載客車輛暫停行駛與接人，空閒車輛不接新任務。所有離線車輛均不接新任務。
- 乘客 Client 使用獨立網頁，供乘客送出乘車請求並查看自己的請求狀態。
- 第一版乘客免登入，網頁自動保存乘客識別碼，重新整理後仍可查看自己的請求；自動生成的每筆請求代表一位新的模擬乘客。
- 提供「新增乘客」入口，每次開出的乘客頁面代表不同乘客；重新整理該頁保留原乘客身分，可於本機同時使用多個乘客頁面。
- 手動請求由乘客在地圖依序點選上車點、下車點，再輸入乘車人數；地圖以不同標記呈現兩個位置。
- 隨機時間自動生成乘車請求由獨立 Python 乘客模擬程式負責，由操作者啟動／停止；乘客網頁不提供持續自動生成的操作。
- 乘客網頁提供一鍵產生並送出一筆隨機乘車請求，由 Server 依派車規則處理。
- 單筆隨機與自動生成共用可設定的起訖地理範圍；預設沿用舊專案台北市範圍：經度 `121.5102～121.5693`、緯度 `25.03068～25.06026`。
- 單筆隨機與自動生成的人數均從 1 人到車隊最大載客上限間隨機抽取；預設四人座車隊時為 1～4 人。
- 隨機起訖直線距離至少 200 公尺，最多抽樣 20 次；找不到符合條件的位置即回報生成失敗，該次不送單。最短距離與抽樣次數可設定。
- 自動生成每筆請求的間隔預設隨機落在 5～15 秒，可設定最短與最長間隔。
- 自動生成預設最多產生 20 筆請求，達到上限即停止；總筆數可設定。
- Server 統一規劃接人與送人的道路路線，再交給 Python 車輛 Client 模擬。
- 第一版 Server 使用單一 worker，透過非同步 HTTP 查詢道路路線，並提供可設定的查詢併發上限。
- 勤崴 Routes REST 服務的實際憑證、使用權限與限制仍須於整合時驗證。
- 若確認接人或送人任一段沒有可行道路路線，將該乘車請求與接送任務標為失敗並顯示原因，釋放原先保留的車輛，讓其他請求繼續處理。
- 路線查詢遇到 HTTP 逾時或暫時性服務錯誤，每次最多等待 10 秒、最多嘗試三次；仍失敗則結束該請求與任務。等待時間與嘗試次數可設定。
- 監控頁顯示所有車輛，側欄提供車隊、乘車請求與任務列表；選取車輛後顯示其路線與起訖點，可定位或跟隨該車，並提供即時速度控制。
- 網頁無法連線 Server 時保留最後資料並標示連線中斷；乘客模擬程式暫停送單，恢復後繼續剩餘筆數，不補發斷線期間的請求。

## 車輛離線與恢復

Q43、Q45 已取代 Q32 中離線立即判定任務失敗的規則；Q36 的恢復後放棄舊任務、回到 Server 最後確認位置的規則亦不再適用於同一輪暫時斷線。Server 保留指派關係並等待進度確認，Client 依是否載客決定繼續送人或暫停。

Client 保存同一輪暫時斷線期間的進度與送達結果，恢復後依原任務回報。已送達則由 Server 確認完成；尚未送達則同步目前位置後續行，不回退到斷線前的位置。未載客車輛須先確認原任務仍有效，才能繼續接人；同一完成結果重複回報只處理一次。

Client 程式已結束或連線一直無法恢復時，第一版保持原任務進度待確認，由操作者重新開始整場模擬處理。

## 斷線人工驗收設計

目前僅有規格，以下為實作後的人工驗收情境，尚未執行。暫時斷線須只阻斷指定車輛 Client 的 HTTP 連線，保持 Server 與該 Client 程式執行；直接停止 Server 並重啟會開始新一輪，無法驗證同一輪暫時斷線。

| 情境 | 操作 | 已確認的預期 |
| --- | --- | --- |
| 載客前斷線 | 車輛前往接人時阻斷其 HTTP 連線，持續超過離線門檻 | Client 暫停行駛與接人；Server 標示離線與進度待確認，保留原任務，不轉派同一請求 |
| 載客後斷線 | 開始載客行駛後阻斷其 HTTP 連線，持續超過離線門檻 | Client 沿已取得路線完成送達後原地等待；Server 仍顯示最後確認資料與進度待確認，不提前判定失敗或完成 |
| 檢查指派關係 | 車輛失聯時另外送出請求，保持其他車輛連線 | 失聯車輛不接新任務；其他空閒車輛可接新請求，原失聯任務不重複指派 |
| 未送達時恢復 | 恢復同一輪 HTTP 連線，回報原任務的目前位置與進度 | Server 核對原任務，從目前位置續行，不回退；未載客車輛須先確認任務有效再接人 |
| 已送達後恢復 | 等離線載客車輛送達後才恢復 HTTP 連線 | Server 核對原任務與送達結果，只確認完成一次，車輛從下車點恢復接單 |
| 重複完成回報 | 車輛已接下一筆任務後，重送上一筆完成結果 | 上一筆不重複完成，新任務與指派不被清除，車輛不被錯誤釋放 |
| 全體 Client 暫時無法連線 | 同一輪模擬中暫時阻斷 HTTP，保持程序執行 | 網頁保留最後資料並顯示中斷；生成器暫停，恢復後繼續剩餘筆數，不補發 |
| Client 結束或永久失聯 | 結束車輛 Client，或持續阻斷 HTTP | 原任務保持待確認，直到操作者重新開始整場模擬 |
| Server 重啟 | 停止並重新啟動 Server，重新啟動相關 Client | 清空舊資料、車輛回初始位置、開始新一輪，舊任務不延續 |
| 新一輪隔離 | Server 重啟後重送上一輪的進度或完成結果 | 舊回報不得更新新一輪的車輛、請求或任務 |

## 第一版完整人工驗收範圍

- 使用三台車與多個獨立乘客頁面，驗證手動地圖選點、單筆隨機、各乘客查看自己的請求，以及重新整理保留身分。
- 啟動乘客模擬程式，驗證預設 5～15 秒間隔、最多 20 筆後停止、隨機人數與起訖限制，以及生成失敗時不送單。
- 驗證空閒車輛最近距離選擇、請求送出順序、容量限制、無合適空閒車輛時等待，以及略過暫時無法服務的請求並保留順位。
- 驗證規劃路線、接人、送達、完成後停在下車點；監控頁選車、定位／跟隨、任務路線與起訖標記，以及各列表更新。
- 在行駛中調整全車速度，驗證進度不中斷、位置不重置，且回報／網頁更新與請求生成仍使用真實時間；關閉監控頁不影響車輛 Client 運作。
- 驗證等待派車時取消成功；若取消與派車交錯，結果只能是取消成功且不執行，或已開始規劃而拒絕取消。
- 驗證無可行路線、暫時性查詢錯誤的等待／嘗試上限，以及失敗原因與車輛釋放。
- 執行上述斷線、恢復、重複完成、新一輪隔離與無法恢復的驗收情境。

第一版依預設三台車驗收；上百台車的效能驗證與忙碌車輛後續任務預約屬後續階段。

## 整合前查核

- 勤崴 Routes REST 憑證與服務權限、查詢頻率／併發限制，以及對應的初始併發設定。
- 官方路線結果的座標格式、encoded polyline 解碼與距離／時間欄位，須以文件與實際回應核對。
- mapThree 1.4.3 使用同一模型 URL、不同模型 id 時，各車模型位置／朝向的獨立性與顯示效果須實際驗證。

這些是整合時待查證的事實，不代表已完成可用性或效能驗證。

## 設定與生效方式

下列設定的生效方式已確認。

| 設定 | 已確認的預設值或規則 | 生效方式 |
| --- | --- | --- |
| 全車速度倍率 | 10 倍 | 監控頁即時調整 |
| 車輛數量 | 3 台 | 重新啟動模擬 |
| 各車載客上限 | 4 人 | 重新啟動模擬 |
| 各車初始位置 | 不同固定位置，可設定 | 重新啟動模擬 |
| 全車回報間隔 | 1 秒 | 重新啟動模擬 |
| 全網頁更新間隔 | 1 秒 | 重新啟動模擬 |
| 車輛離線門檻 | 10 秒 | 重新啟動模擬 |
| 路線查詢等待上限 | 每次 10 秒 | 重新啟動模擬 |
| 路線查詢嘗試次數 | 最多 3 次 | 重新啟動模擬 |
| 路線查詢併發上限 | 可設定，預設值尚待整合確認 | 重新啟動模擬 |
| 共用隨機起訖範圍 | 舊專案台北市範圍 | 重新啟動模擬 |
| 隨機起訖最短直線距離 | 200 公尺 | 重新啟動模擬 |
| 隨機起訖抽樣上限 | 20 次 | 重新啟動模擬 |
| 自動生成間隔 | 5～15 秒 | 重新啟動乘客模擬程式 |
| 自動生成總數 | 最多 20 筆 | 重新啟動乘客模擬程式 |

重新啟動模擬包含重新啟動 Server 與相關 Client；依既定需求，Server 重啟會清空模擬資料。重新啟動乘客模擬程式不需要清空 Server 資料。

## 後續演算法需求

使用者提出未來可能比較空閒車輛執行新任務的完成時間，以及忙碌車輛完成現有任務後再執行新任務的完成時間，選擇較快方案。

第一版先維持只指派空閒車輛，將選車邏輯集中在可替換的派車模組；忙碌車輛的後續任務預約與時間比較留到下一階段。
