# 車輛監控系統規格

Status: draft

## 既定規範

- 前端使用 Vite + Vanilla JavaScript（HTML / CSS），後端使用 Python + FastAPI，通訊統一使用 HTTP。
- Server 管理車輛、需求與任務資料；車輛 Client 負責模擬及回報狀態；乘客 Client 負責提出需求；監控網頁負責顯示 Server 資料。
- 地圖與 3D 模型顯示留在前端；第三方 SDK / API 須以官方文件確認。
- `../kwmap-practice/` 僅供讀取與參考；所有修改限於本專案。

## 已確認需求

- 乘車請求包含上車點、下車點與乘車人數。
- 第一版以同一台電腦執行 Server、車輛 Client、乘客 Client 與監控網頁，完成模擬展示。
- 使用模擬車輛與乘客資料。
- Server 使用記憶體保存資料；重啟後清空車輛狀態、需求與任務，重新開始模擬。
- 乘客送出乘車請求後，由 Server 自動派車；有空閒車輛時指派，否則等待。
- 一個接送任務由一台車執行一筆乘車請求，包含前往上車點、接人與送達下車點；每台車同時只執行一個任務。
- 乘客可見流程為「等待派車 → 規劃路線 → 前往接人 → 載客行駛 → 完成」；異常時顯示「失敗」。第一版抵達上車點即開始送人，抵達下車點即完成，不額外等待上下客。
- 乘客只能取消「等待派車」的請求，開始規劃路線後不能取消；保留「已取消」紀錄。
- 第一版不安排共乘，也不讓車輛同時承接多筆乘車請求。
- 車輛 Client 使用獨立 Python 程式模擬行駛並透過 HTTP 回報；關閉監控網頁不影響模擬執行。
- 地圖與車輛 3D 模型沿用舊專案；SDK / API 整合仍須依官方文件確認。
- 將舊專案車輛模型複製至本專案 `public/models/car/`，並以 `.gitignore` 排除 `public/models/`，不納入 Git 追蹤。
- 第一版按送出順序掃描等待請求，從符合條件的空閒車輛中，以到上車點的直線距離選擇最近的一台；實際行駛路線另外規劃。暫時無法服務的請求保留原順位，允許先處理後面可被服務的請求。
- 每台車有載客上限，只能承接人數未超過上限的乘車請求；超過整個車隊最大載客上限的請求直接拒絕。若合適車輛忙碌，請求繼續等待。
- 車隊預設三台車，可透過設定調整數量。
- 每台車預設最多載四人，可分別設定各車載客上限。
- 各車使用不同固定初始位置，可透過設定調整；每次重新開始模擬均回到設定位置。
- 車輛行駛共用速度倍率，預設 10 倍且可設定；乘車請求生成間隔仍以真實時間計算。
- 速度倍率須可在模擬執行中即時調整；其他設定的生效方式逐項確認，不統一要求重啟。
- 送達乘客後，車輛停在下車點並恢復空閒，從該位置承接下一筆任務，不自動返回初始位置。
- 車輛每秒回報一次位置、朝向與任務進度；監控與乘客網頁每秒透過 HTTP 更新一次。頻率可設定，採全域設定並區分車輛回報間隔與網頁更新間隔；兩者均以真實時間計算，不受行駛速度倍率影響。
- 車輛超過 10 秒未回報即標為離線並排除派車；若正在執行任務，將該任務與請求標為失敗，不自動轉派。離線門檻可設定。
- 乘客 Client 使用獨立網頁，供乘客送出乘車請求並查看自己的請求狀態。
- 手動請求由乘客在地圖依序點選上車點、下車點，再輸入乘車人數；地圖以不同標記呈現兩個位置。
- 隨機時間自動生成乘車請求由獨立 Python 乘客模擬程式負責，由操作者啟動／停止；乘客網頁不提供持續自動生成的操作。
- 乘客網頁提供一鍵產生並送出一筆隨機乘車請求，由 Server 依派車規則處理。
- 單筆隨機與自動生成共用可設定的起訖地理範圍；預設沿用舊專案台北市範圍：經度 `121.5102～121.5693`、緯度 `25.03068～25.06026`。
- 自動生成每筆請求的間隔預設隨機落在 5～15 秒，可設定最短與最長間隔。
- 自動生成預設最多產生 20 筆請求，達到上限即停止；總筆數可設定。
- Server 統一規劃接人與送人的道路路線，再交給 Python 車輛 Client 模擬。
- 第一版 Server 使用單一 worker，透過非同步 HTTP 查詢道路路線，並提供可設定的查詢併發上限。
- 勤崴 Routes REST 服務的實際憑證、使用權限與限制仍須於整合時驗證。
- 若確認接人或送人任一段沒有可行道路路線，將該乘車請求與接送任務標為失敗並顯示原因，釋放原先保留的車輛，讓其他請求繼續處理。
- 路線查詢遇到 HTTP 逾時或暫時性服務錯誤，每次最多等待 10 秒、最多嘗試三次；仍失敗則結束該請求與任務。等待時間與嘗試次數可設定。

## 設定與生效方式

速度倍率即時可調已確認；其餘生效方式是供使用者檢視的建議，尚未確認。

| 設定 | 已確認的預設值或規則 | 建議生效方式 |
| --- | --- | --- |
| 全車速度倍率 | 10 倍 | 執行中即時調整 |
| 車輛數量 | 3 台 | 重新啟動模擬 |
| 各車載客上限 | 4 人 | 重新啟動模擬 |
| 各車初始位置 | 不同固定位置，可設定 | 重新啟動模擬 |
| 全車回報間隔 | 1 秒 | 重新啟動模擬 |
| 全網頁更新間隔 | 1 秒 | 重新啟動模擬 |
| 車輛離線門檻 | 10 秒 | 重新啟動模擬 |
| 路線查詢等待上限 | 每次 10 秒 | 重新啟動模擬 |
| 路線查詢嘗試次數 | 最多 3 次 | 重新啟動模擬 |
| 路線查詢併發上限 | 可設定，預設值尚待整合確認 | 重新啟動模擬 |
| 共用隨機起訖範圍 | 舊專案台北市範圍 | 重新啟動模擬 |
| 自動生成間隔 | 5～15 秒 | 重新啟動乘客模擬程式 |
| 自動生成總數 | 最多 20 筆 | 重新啟動乘客模擬程式 |

重新啟動模擬的建議方式包含重新啟動 Server 與相關 Client；依既定需求，Server 重啟會清空模擬資料。重新啟動乘客模擬程式不需要清空 Server 資料。

## 後續演算法需求

使用者提出未來可能比較空閒車輛執行新任務的完成時間，以及忙碌車輛完成現有任務後再執行新任務的完成時間，選擇較快方案。

第一版先維持只指派空閒車輛，將選車邏輯集中在可替換的派車模組；忙碌車輛的後續任務預約與時間比較留到下一階段。

## 尚待釐清

速度以外設定的生效時機、隨機請求的人數與起訖距離限制、車輛恢復連線處理、乘客識別、監控操作及驗收情境尚未確認；本文件仍在討論中。
