# 車輛監控系統第一版規格

Status: awaiting-validation
Approval: confirmed

## 問題陳述（Problem Statement）

操作者需要在本機觀察多台模擬車輛如何受理乘客的乘車請求、派車、接人與送達。舊專案將單車模擬、乘車請求與地圖顯示集中在同一網頁，無法呈現獨立 Server、車輛 Client 與乘客 Client 的分工，也無法在關閉監控頁後繼續模擬。

第一版需要讓多個乘客頁面與自動生成程式共用 Server 管理的資料，呈現多車派遣、容量與排隊、即時速度控制，以及斷線後不同接送階段的行為。操作者也需要明確的設定生效方式與人工驗收條件，方便重現同一種情境。

## 解決方案（Solution）

建立本機 Client / Server 車輛監控系統。Server 管理車輛、乘車請求與接送任務，自動選車並規劃道路路線；獨立 Python 車輛 Client 沿路線模擬與回報，乘客網頁負責送單與查看自己的請求，獨立 Python 乘客模擬程式負責限量自動生成。監控網頁顯示 Server 資料，呈現勤崴地圖與車輛 3D 模型。

預設使用三台四人座車輛與 10 倍行駛速度。操作者可即時調整全車速度；其餘設定依設定表重新啟動生效。Server 使用記憶體保存資料，重啟即開始新一輪模擬。

暫時斷線時，已載客車輛沿已取得路線送達，未載客車輛暫停接送。Server 保留失聯車輛的原任務並標示進度待確認，恢復連線後核對結果，避免重複派車或重複完成。

## 使用者故事（User Stories）

1. 身為操作者，我希望在同一台電腦啟動 Server、各 Client 與監控網頁，以便完成本機接送模擬展示。
2. 身為操作者，我希望預設使用三台車，以便觀察多車派遣與全部忙碌時的等待情境。
3. 身為操作者，我希望調整車輛數量，以便依展示需求改變車隊規模。
4. 身為操作者，我希望各車預設載客上限四人且可分別設定，以便觀察不同容量的派車結果。
5. 身為操作者，我希望各車使用不同且可設定的固定初始位置，以便重現與比較派車結果。
6. 身為操作者，我希望重新開始時各車回到初始位置，以便從相同起點進行下一輪模擬。
7. 身為乘客，我希望免登入即可開啟乘客網頁，以便直接提出模擬乘車請求。
8. 身為操作者，我希望每次透過新增乘客入口開啟的頁面代表不同乘客，以便同時模擬多位乘客。
9. 身為乘客，我希望重新整理網頁後保留乘客身分，以便繼續查看自己的請求。
10. 身為乘客，我希望在地圖依序選取上車點與下車點並看到不同標記，以便確認接送起訖位置。
11. 身為乘客，我希望輸入乘車人數，以便 Server 選擇載客上限足夠的車輛。

18. 身為乘客，我希望有合適車輛但正在忙碌時繼續等待，以便稍後有車可用時受理請求。

44. 身為操作者，我希望未載客車輛斷線時停止行駛與接人，以便恢復後先核對任務再執行。
45. 身為操作者，我希望 Server 保留離線車輛的原任務並標示進度待確認，以便避免未收到回報就判定失敗或重複派車。
46. 身為操作者，我希望恢復連線後依原任務核對進度或送達結果，以便從目前位置續行或確認完成。
47. 身為操作者，我希望同一完成結果重複回報只處理一次，以便上一筆任務的回報不干擾下一筆。
48. 身為操作者，我希望網頁斷線時保留最後資料並標示中斷，以便知道畫面資料尚未更新。

52. 身為後續開發者，我希望選車演算法集中在可替換的派車模組，以便日後擴充完成時間比較而不將選車規則散落在各 Client。

## 實作決策（Implementation Decisions）

### 架構與模組分工

- 前端使用 Vite + Vanilla JavaScript（HTML / CSS），後端使用 Python + FastAPI，通訊統一使用 HTTP。地圖與 3D 模型顯示留在前端。
- Server 是車輛、乘車請求、接送任務與本輪模擬狀態的管理者。第一版採單一 worker 與記憶體保存；多 worker 不在此版範圍。
- Server 內集中管理乘車請求受理／取消、派車、路線規劃、車輛進度核對與設定提供。派車模組集中決定選車，任務管理負責指派關係與狀態轉換。
- 車輛 Client 是獨立 Python 程式，保存各車的位置、朝向、任務與行駛進度，沿 Server 提供的路線模擬並回報。多車狀態須分別保存，不沿用舊專案的單車全域狀態。
- 乘客網頁負責手動選點、乘車人數輸入、送單、單筆隨機送單、查看自己的請求與取消等待請求。
- 乘客模擬程式是獨立 Python 程式，由操作者啟停持續自動生成；乘客網頁不提供持續生成的操作。
- 監控網頁顯示 Server 資料，選車、定位／跟隨與速度控制均在前端操作，行駛由車輛 Client 執行。

### 資料與 HTTP 互動契約

以下定義必要語意，實際端點名稱、資料欄位拼字與模組內部形式留待實作，不假設尚不存在的介面。

| 資料／操作 | 必要內容與結果 |
| --- | --- |
| 模擬輪次 | Server 重啟開始新一輪；Client 回報須能區分輪次，舊輪次的進度與完成結果不得更新新資料 |
| 車輛 | 可識別各車；包含載客上限、初始與目前位置、朝向、最後回報時間、連線狀態與目前任務關係 |
| 乘車請求 | 可識別各筆及提出者；包含上車點、下車點、乘車人數、送出順序、處理狀態與失敗／取消結果 |
| 接送任務 | 可識別各筆；一筆連結一台車與一筆請求，包含接人與送人路線、執行階段、進度與送達確認 |
| 提出請求 | 接收乘客、起訖點與人數，受理後進入等待；超過整個車隊最大載客上限則拒絕 |
| 取消請求 | 僅等待派車可取消；取消與派車交錯時，結果只能是取消成功且不執行，或規劃已開始而拒絕取消 |
| 車輛取得任務 | Server 提供該車的有效任務與路線；每台車同時只執行一筆，不接忙碌車輛的預約任務 |
| 車輛回報 | 回報所屬輪次、車輛與任務，以及位置、朝向、進度或送達結果；Server 核對原任務，不讓舊／重複結果破壞新指派 |
| 讀取資料 | 乘客網頁查看自己的請求；監控頁查看整個車隊、請求與任務。免登入識別用於本機模擬，不視為正式存取控制 |
| 取得設定／調速 | 全域設定由 Server 統一提供；監控頁修改全車速度，各車於正常 HTTP 互動取得更新，不重置任務進度 |

### 請求、派車與接送流程

- 乘車請求包含上車點、下車點與乘車人數。提出者是乘客，乘車人數可包含同行者。
- Server 收到請求後自動派車，按送出順序掃描等待請求。從載客上限足夠且空閒的車輛中，選擇距上車點直線距離最近的一台；實際行駛路線另外規劃。
- 暫時無法服務的請求保留原順位，允許先處理後面可服務的請求。有合適車輛但正在忙碌時繼續等待；超過整個車隊最大載客上限則直接拒絕。
- 每台車同時只執行一個接送任務，一個任務執行一筆乘車請求，不共乘或同時接多筆請求。
- 乘客可見流程為「等待派車 → 規劃路線 → 前往接人 → 載客行駛 → 完成」。規劃期間保留車輛，不能同時重複指派給其他請求。
- 第一版不額外等待上下客，抵達上車點即開始送人，抵達下車點即送達；Server 核對送達結果後確認任務完成。
- 任務完成後車輛停在下車點，恢復空閒並從該位置承接下一筆，不自動返回初始位置。斷線期間已送達仍須等待恢復連線與完成核對才可接單。
- 已確認的路線規劃失敗顯示「失敗」並保留原因；等待期間取消成功顯示「已取消」並保留紀錄。離線任務以「進度待確認」呈現，不因逾時立即失敗。
- 派車模組保留選車邏輯的替換位置。未來比較空閒車執行新任務與忙碌車完成現有任務後接續新任務的完成時間，仍需另行擴充預約與任務管理。

### 地圖、道路路線與監控

- 沿用勤崴地圖與舊專案車輛 3D 模型；模型已複製到本專案並以 Git 忽略規則排除，不納入版本控制。舊專案僅供唯讀參考，所有修改限於本專案。
- 各車使用獨立模型 id 與狀態，可共用模型檔；同 URL 多模型的獨立位置與朝向須在整合時實測。
- Server 使用勤崴官方 Routes REST 規劃接人與送人路線，再交給 Python 車輛 Client。路線取得不依賴監控頁開啟。
- Server 以非同步 HTTP 查詢路線，查詢併發上限可設定。服務權限、配額與頻率限制須依官方文件與實際可用憑證查核，未確認前不承諾特定吞吐量。
- 確認接人或送人任一段無可行路線時，將請求與任務標為失敗、顯示原因並釋放保留車輛，讓其他請求繼續。
- HTTP 逾時或暫時性路線服務錯誤，每次最多等待 10 秒、最多嘗試三次；仍失敗則結束請求與任務，保留原因並釋放車輛。等待時間與次數可設定。
- 監控地圖顯示所有車輛；側欄提供車隊、乘車請求與接送任務列表。選車後顯示該車路線與起訖點，可定位或跟隨。
- 各網頁以 HTTP 讀取 Server 資料，預設每秒更新。頁面文字精簡，避免重複說明可由操作或元件狀態理解的資訊。

### 乘客識別與隨機生成

- 第一版免登入，乘客網頁自動保存識別碼，重新整理仍能查看自己的請求。「新增乘客」入口每次開出的頁面代表不同乘客，可在本機同時使用多頁。
- 手動請求依序在地圖選取上、下車點，輸入人數並送出；起訖使用不同標記。隨機起訖的最短距離限制不擅自擴大為手動請求規則。
- 單筆隨機是一鍵產生並送出一筆請求，之後由 Server 自動派車，不是隨機指派已有請求。
- 單筆隨機與自動生成共用可設定的地理範圍與生成規則。預設經度 121.5102～121.5693、緯度 25.03068～25.06026，沿用舊專案台北市範圍。
- 隨機人數取 1 人至車隊最大載客上限，預設車隊為 1～4 人。
- 隨機起訖直線距離至少 200 公尺，最多抽樣 20 次。找不到符合條件的位置就回報生成失敗、該次不送單；距離與次數可設定。
- 自動生成每筆代表新的模擬乘客，預設間隔 5～15 秒、最多 20 筆後停止；總數與間隔可設定。生成量有上限，不無限累積。

### 模擬速度、更新與設定

- 車隊預設三台車，每台載客上限四人，可分別調整容量。各車使用不同固定初始位置，可設定，每次重新開始回到設定位置。
- 全車共用行駛速度倍率，預設 10 倍，監控頁可在執行中調整；從目前進度繼續，不重置車位、任務或已完成路段。
- 車輛預設每秒回報位置、朝向與任務進度。全車回報間隔與全網頁更新間隔是不同的全域設定，預設均為 1 秒。
- 回報、網頁更新、自動生成間隔與離線門檻均以真實時間計算，不受行駛速度倍率影響。

| 設定 | 預設值或規則 | 生效方式 |
| --- | --- | --- |
| 全車速度倍率 | 10 倍 | 監控頁即時調整 |
| 車輛數量 | 3 台 | 重新啟動模擬 |
| 各車載客上限 | 4 人 | 重新啟動模擬 |
| 各車初始位置 | 不同固定位置，可設定 | 重新啟動模擬 |
| 全車回報間隔 | 1 秒 | 重新啟動模擬 |

| 路線查詢嘗試次數 | 最多 3 次 | 重新啟動模擬 |
| 路線查詢併發上限 | 可設定，初始值待整合查核 | 重新啟動模擬 |

重新啟動模擬包含 Server 與相關 Client，Server 重啟清空本輪車輛狀態、請求與任務。只重新啟動乘客模擬程式不清空 Server 資料。

### 暫時斷線、恢復與新輪次

| 對象／階段 | 無法連線 Server 時的行為 |
| --- | --- |
| 已載客車輛 | 沿已取得的送人路線完成送達，到站後原地等待 |
| 尚未載客車輛 | 暫停行駛與接人，等待恢復後確認原任務有效 |
| 空閒車輛 | 不接新任務 |
| Server | 超過 10 秒未回報標示車輛離線、排除派車；保留原任務與指派，標示進度待確認，不立即失敗或轉派 |
| 監控與乘客網頁 | 保留最後資料並標示連線中斷 |
| 乘客模擬程式 | 暫停送單；恢復後繼續剩餘筆數，不補發斷線期間的請求 |

- Client 保存同一輪暫時斷線期間的進度與送達結果。恢復後按原任務回報，已送達由 Server 核對後確認完成；尚未送達則同步目前位置後續行，不退回 Server 的斷線前位置。
- 未載客車輛恢復後，先確認原任務仍有效才繼續接人。Server 最後回報可能仍是前往接人，但 Client 已載客，因此不能只看 Server 最後階段就立即失敗或轉派。
- 同一完成結果重複回報只處理一次。車輛已接下一筆時，上一筆重複完成不得清除新任務或錯誤釋放車輛。
- Client 結束或永久失聯時，第一版保持原任務進度待確認，由操作者重新開始整場模擬。
- Server 重啟即新一輪：清空舊資料、車輛回初始位置、生成器重新啟動，不恢復舊任務。上一輪的延遲進度或完成結果不得更新新一輪同名車輛或任務。
- 本節取代早期 Q32 的離線立即失敗及 Q36 的恢復後放棄舊任務、回退位置；討論歷史只保存在 Comments，現行行為以本節為準。

### 完整人工驗收

| 情境 | 操作與預期 |
| --- | --- |
| 本機多車多乘客 | 啟動預設三台車並開啟多個新增乘客頁面；各頁不同身分、重新整理保留身分，手動選點標記正確、可查看自己的請求 |
| 隨機送單 | 一鍵只送一筆；驗證範圍、人數、最短距離與抽樣上限；生成失敗不送單 |
| 限量自動生成 | 啟動 Python 生成器，依真實時間每 5～15 秒送單、預設最多 20 筆停止，每筆代表新模擬乘客；可由操作者停止 |
| 選車與等待 | 送出多筆請求，驗證送出順序、符合容量的空閒車輛最近直線距離選擇、全忙時等待、略過暫不可服務者並保留順位 |
| 容量拒絕 | 送出超過整個車隊最大載客上限的請求，應拒絕；有合適車但忙碌時應等待 |
| 完整接送 | 等待、規劃、接人、載客、送達與完成依序呈現；不額外等待上下客，確認完成後從下車點接新任務 |
| 監控互動 | 顯示所有車與三種列表；選車顯示路線與起訖，定位／跟隨操作正確，多車位置與朝向互不影響 |
| 即時調速 | 行駛中修改速度，進度不中斷且位置不重置；回報、網頁更新與生成間隔仍按真實時間 |
| 網頁生命週期 | 關閉監控網頁，車輛繼續執行；重新開啟後可讀取 Server 當前資料 |
| 取消與派車交錯 | 等待時取消成功，規劃開始後拒絕；不能同時顯示已取消並執行接送 |
| 無路線與查詢錯誤 | 任一接送路段無可行路線時失敗並釋放車輛；暫時錯誤遵守每次等待與最多嘗試上限、保留失敗原因 |
| 載客前斷線 | 僅阻斷指定車輛 HTTP、程序持續執行，超過離線門檻；Client 暫停接人，Server 離線／進度待確認且保留任務 |
| 載客後斷線 | 同樣阻斷載客車 HTTP；Client 繼續送達後原地等待，Server 保留最後資料，不提前判失敗或完成 |
| 失聯時新請求 | 其他車保持連線，新增請求可派給其空閒車；失聯車不接新單，原請求不重複指派 |
| 未送達時恢復 | 恢復同輪連線，按原任務核對目前位置與進度後續行，不回退；未載客先確認有效任務 |
| 已送達後恢復 | 恢復後核對原任務與送達結果，只確認完成一次，從下車點恢復接單 |
| 重複完成回報 | 已接下一筆任務後重送上一筆完成，新任務與指派保持有效，車輛不被錯誤釋放 |
| 網頁與生成器斷線 | 暫時阻斷 HTTP 且程序持續執行；網頁保留最後資料與中斷標示，生成器暫停，恢復後不補發並繼續剩餘量 |
| 永久失聯 | 結束 Client 或持續阻斷連線，原任務保持待確認，直到操作者重啟整場模擬 |
| Server 重啟與隔離 | 重啟 Server 與相關 Client，舊資料清空、車回初始位置；重送上一輪結果不得更新新輪次 |

暫時斷線驗收須只阻斷 HTTP，保持 Server 與 Client 程序存活；直接停止並重啟 Server 會開始新一輪，不能驗證同一輪斷線。第一版按預設三台車驗收，以上應用程式驗收目前尚未執行。
