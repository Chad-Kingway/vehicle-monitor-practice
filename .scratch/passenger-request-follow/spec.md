Status: ready-for-agent

## 問題陳述

監控操作者目前只能透過「新增乘客」開啟乘客頁，再在該頁操作。若要快速展示一筆隨機乘車請求，需要多做一步。乘客完成、取消或遇到失敗後雖可重新選點，但輪詢會把新選點覆蓋成上一筆請求的起訖。乘客也只能一次性定位承接車，無法持續追蹤其位置。

## 解決方案

監控頁提供「隨機送出一筆」入口，另開一個具有新乘客身分的乘客頁，並在首次成功連線後自動提出一筆隨機請求。乘客頁原有的隨機送單入口維持不變。

乘客地圖使用 Server 為接送任務規劃的道路路線，於接人與載客階段顯示各自路線。前一筆請求終止後，乘客可重新選點並提出下一筆；等待期間的輪詢保留新選點，新請求則顯示 Server 指派的承接車。乘客可開啟或關閉承接車跟隨，請求終止時自動停止。

## 使用者故事

1. 身為監控操作者，我希望從監控頁快速開啟一筆隨機乘車請求，以便直接展示系統受理隨機需求的流程。
2. 身為監控操作者，我希望每次快速送單都使用新的乘客身分，以便新請求不會與另一乘客的進行中請求互相衝突。
3. 身為乘客，我希望監控頁開啟的乘客頁在連線成功後自動提出一筆隨機請求，以便無須再按一次送出。
4. 身為乘客，我希望保留乘客頁既有的隨機送單入口，以便仍可在乘客頁自行提出隨機需求。
5. 身為乘客，我希望在前往接人階段看到 Server 規劃的接人道路路線，以便查看承接車前往上車點的路段。
6. 身為乘客，我希望在載客階段看到 Server 規劃的送人道路路線，以便查看車輛前往下車點的路段。
7. 身為乘客，我希望在目前請求完成、取消或失敗後重新選擇上車點與下車點，以便提出下一筆乘車需求。
8. 身為乘客，我希望在新選點後仍看到自己選擇的位置，以便網頁輪詢不會還原成上一筆請求的起訖。
9. 身為乘客，我希望新請求顯示 Server 實際指派的承接車，以便車輛位置與請求關聯一致。
10. 身為乘客，我希望開啟或關閉持續跟隨承接車，以便依需求追蹤車輛或自行查看地圖。
11. 身為乘客，我希望請求終止時自動停止跟隨，以便地圖不會繼續追蹤已結束請求的車輛。
12. 身為乘客，我希望每位乘客仍同時最多只有一筆進行中的請求，以便新請求不會與尚未終止的接送任務重疊。
13. 身為乘客，我希望路線、車輛位置及請求狀態來自同一筆 Server 請求與接送任務，以便頁面不會混合前一筆與下一筆接送資料。

## 實作決策

- 延續既有 Client / Server 與 HTTP 通訊；Server 管理乘車請求、接送任務與承接車關聯，前端呈現資料及地圖。
- 監控頁的快速入口為每次操作建立新的乘客身分並另開乘客頁。新頁首次成功取得 Server 狀態後自動送出一筆隨機請求，乘客頁原有隨機按鈕不變。
- 自動送出沿用既有乘客頁請求識別及不明結果恢復流程；一次性啟動狀態在送出前消耗，避免重新整理重複建立請求。
- 維持每位乘客最多一筆進行中的乘車請求。只有目前請求完成、取消或失敗後才可準備下一筆；新選點在尚未送出期間不受輪詢覆寫。
- 新請求的承接車依 Server 回傳的該請求 `vehicle_id` 選取，車位沿用車輛 Client 最近一次回報的位置，不在乘客頁自行選車或計算道路路線。
- 接人及送人路線沿用 Server 接送任務既有的兩段道路路線，依目前接送階段切換顯示。
- 乘客頁跟隨控制操作既有地圖跟隨行為；更換目前請求或請求終止時清除舊跟隨目標。
- 不新增 API、資料結構或領域決策；不新增測試接點。

## 測試決策

- 測試應驗證外部行為及 Server／畫面資料關聯，不檢查內部函式呼叫或實作細節。
- 使用既有最高接點：本機瀏覽器與現有 Server、車輛 Client 進行端到端人工驗收。涵蓋監控頁觸發隨機送單、乘客頁路線階段切換、終止後重新選點及新承接車、持續跟隨與停止。
- 同時核對 Server 中請求的乘客身分、起訖、`vehicle_id` 及任務路線，確認畫面顯示與受理資料一致。
- 現有專案沒有自動測試指令或測試檔；不新增測試檔或測試接點。既有人工驗收文件提供瀏覽器與 HTTP 驗證方式，依相同作法補充本規格情境。

## 不在範圍內

- 修改乘客頁原有的隨機送單行為。
- 修改 Server 派車規則、接送路線規劃方式、第三方地圖服務或車輛 Client 回報契約。
- 允許進行中的乘車請求修改起訖、人數或提出第二筆請求。
- 乘客頁顯示歷史請求清單或加入新的承接車選擇功能。
